# 数据同步 — 远期架构设计

> 现状（v0.10）：anki-forge 不持有用户状态——材料文件在用户手里，卡片以
> `.apkg`/TSV 落盘，生成缓存是本机优化（`~/.anki-forge/cache-v1.json`）。
> 跨设备同步的最小单元天然存在：**导出的文件本身**。本文记录将来做同步时
> 的设计决策与边界，避免到时拍脑袋。

## 原则

1. **文件是同步单元**。`.apkg`（完整牌组）与 TSV（纯文本）都已可导入 Anki
   全平台——同步优先复用它们，不发明私有格式。
2. **服务器不碰材料**。隐私姿态与现在一致：文本只发往用户自己选的 LLM。
   任何同步方案默认无服务器（git/网盘/WebDAV），而不是自建云。
3. **缓存不参与同步**。`cache-v1.json` 是本机性能优化，键含 chunk 哈希，
   跨机器命中率本就不同，同步它没有价值。

## 候选路线（按成本排序）

| 路线 | 做法 | 适合 |
|------|------|------|
| 手动（现状） | 导出 .apkg/TSV → 网盘/聊天工具传 | 今天已可用 |
| git 同步 | 把导出目录变成 git 仓库；PC 端 commit，手机 Termux 端 pull | Termux 用户 |
| WebDAV | 同步目录指向坚果云等 WebDAV 服务；CLI 加 `--sync-dir` | 想全自动的用户 |
| AnkiWeb | 依赖 Anki 自带同步：我们只负责把卡写进 Anki，同步交给 Anki | 已用 Anki 的主力方案 |

## 预留的接口位（将来实现时不改架构）

- `writeApkgBytes()` 已是纯函数：任意传输层拿到 bytes 即可落文件。
- Web UI 的 job 结果（cards JSON）序列化即 TSV/apkg 的源，将来加
  `GET /api/job/:id/export?format=…` 之外的历史列表即可。

## 明确不做

- 自建账号体系/云端存储——运营成本与隐私责任都不属于这个项目。
- 同步 Anki 学习进度（复习记录）——那是 AnkiWeb 的职责，不越界。
